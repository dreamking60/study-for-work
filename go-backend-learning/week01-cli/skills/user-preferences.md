# Skills — 用户偏好与协作流程

## 沟通与语气
- **语言**：优先使用中文回复，只有在用户明确要求其他语言时再切换。
- **确认方式**：用户常用“好，然后呢”“可以...吗”之类的问法，希望先快速确认，再进入执行步骤。
- **信息密度**：答案需要开门见山，先说完成了什么，再补细节与下一步建议。
- **执行偏好**：如果用户已经给了足够上下文，优先直接落地修改文档或代码，不要长时间停留在抽象规划层。

## 输出格式偏好
- **路径要求**：在 Markdown 说明里不要使用绝对路径，优先使用相对路径或项目内层级清晰的路径。
- **文件引用**：在说明修改内容时，优先给出简洁路径，并尽量配合 code diff 说明变化。
- **结构**：倾向使用简短小标题 + 列表。对于简单确认可以直接一句话。
- **教程风格**：相比“概念说明”或“高层路线图”，更偏好“直接照着做”的教程，要求包含目录、步骤、命令、停止点和验收标准。

## 常用提问/需求类型
- “请确认项目能否运行” → 期待执行 `go test ./...` 或 `go run` 并反馈结论。
- “把 week/day 的计划细化” → 不只是拆目标，还要改成可直接执行的教程，包含目录、代码落点、命令、验证方式和本阶段先不要做什么。
- “感觉某内容还不够” → 需要在原有基础上增量补充（例如路径调整、Go 速查扩写）。
- “根据参考仓库/官方文档改教程” → 需要真的阅读参考资料，把内容翻译成当前仓库能直接上手的步骤，而不是只做二次总结。

## 工作流程（Go 项目）
1. **先验证环境**：运行 `go test ./...` 或相关命令，确认新环境可执行。
2. **分析现有结构**：使用 `rg --files`、`sed -n` 等快速了解项目内容。
3. **先看正文入口**：当前学习计划正文以 `study-for-work/learning-plan/tutorials/` 为主。
4. **制定或调整计划**：只有在必要时才停在规划层；如果用户要的是教程，就直接产出教程正文。
5. **产出文档**：优先更新 `study-for-work/learning-plan/tutorials/...`，内容要写明目录、步骤、命令、测试、停止点与提示。
6. **附加参考**：为离线场景准备 Go 标准库示例或脚本，集中在 `go-recipes.md` 等文件。
7. **参考资料使用原则**：优先参考官方文档、项目内 README、设计文档；输出时说明借鉴来源和当前实现边界，不要把大仓库整套照搬。

## 验收与交付
- 输出结尾附带“后续建议/下一步”提示，帮助用户接着做事。
- 若某命令无法执行（如权限、无网络），要说明原因并提出替代方案。
- 遇到歧义或目录要求（如路径指定）优先满足用户显式偏好。
- 如果文档体系发生调整，要同步更新 README 和 tutorial 索引，避免正文和索引分裂。
