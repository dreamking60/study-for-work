# Week 03 Day 1：先把“谁能发消息”这件事讲清楚

## 今天你要完成什么
今天你先不要急着写鉴权代码，而是先把“消息入口的身份边界”想明白。

你今天要回答的问题非常简单：
- 什么人可以发消息
- 服务端用什么判断他是合法的
- 这份身份信息放在哪里

## 为什么今天先做设计，不直接写代码
因为你一旦把鉴权接错位置，后面会出现两种问题：
- 本来应该在入口被挡住的消息，已经跑进业务逻辑了
- 每个 handler 都自己判断权限，逻辑越来越重复

所以今天的重点不是写库，而是画边界。

## 今天建议你先写一份最小方案
你不用写很复杂，只要把下面三点写清楚：
1. 消息里带什么身份信息
2. 服务端在什么时机校验
3. 校验通过后，session 里保存什么

## 这一版推荐的最小方案
为了先学会结构，今天建议你先用最小版：
- 消息里带 `token`
- 服务端在 router 前或 router 入口处校验
- 校验通过后，把 `user_id` 和 `expires_at` 放进 session

## 今天你建议补到哪个文件里
你可以先写文档注释，或者先留接口：
- `internal/auth/auth.go`
- `internal/session/session.go`

## 今天完成后的标准
- 你已经决定 token 放在哪
- 你已经决定哪里校验
- 你已经决定 session 保存哪些字段

## 今天会用到的库和最小代码

### 最小 session 字段
```go
type Session struct {
    ConnID    string
    UserID    string
    Token     string
    ExpiresAt time.Time
}
```

### 为什么这里要用 `time.Time`
因为后面会自然进入“会不会过期”这个问题。
