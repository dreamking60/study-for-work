# Week 05 教程：给 `edge-gateway` 补压测、限流和观测

## 本周目标
- 做一轮真实压测
- 加最小限流能力
- 补基础日志和指标

## 本周主要改哪些文件
- `internal/server/server.go`
- `internal/server/router.go`
- 如需要新增 `internal/limit/`
- 如需要新增 `internal/metrics/`

## 本周通过线
- 至少一种限流策略已落地
- 至少一轮压测数据已记录
- 日志字段和基础指标有文档说明

## 第 1 天：选限流位置
你要先决定：
- 连入口限流
- 房间级限流
- 用户级限流

这一版建议先做接入层限流。

今天的停止点：
- 能明确说清“为什么限流放在接入层而不是房间层”

## 第 2 天：实现限流
先用最简单、可解释的方案即可。

完成标准：
- 超限请求会被明确拒绝

建议今天不要追求复杂算法，先实现：
- 固定窗口
或者
- 令牌桶

## 第 3 天：准备压测场景
至少设计 3 组：
- 正常连接
- 突发连接
- 高频消息

完成标准：
- 每组场景都有参数说明

建议至少记下：
- 并发连接数
- 每秒消息数
- 持续时间

## 第 4 天：跑第一轮压测
今天的重点是拿数据，不是拿漂亮数据。

记录：
- 吞吐
- 延迟
- 错误率

今天不要美化结果，先保证数据可复现。

## 第 5 天：补结构化日志
至少有这些字段：
- `request_id` 或 `conn_id`
- `user_id`
- `room_id`
- `latency_ms`

如果今天暂时没有正式指标系统，也至少把日志字段补齐。

## 第 6 天：定位一个热点
你可以用：
- pprof
- 日志统计
- 自己加简单计时

完成标准：
- 至少有一个“发现问题 -> 修改 -> 再验证”的闭环

建议把优化过程写成 4 行：
- 发现了什么
- 怀疑原因是什么
- 改了什么
- 数据有没有变化

## 第 7 天：写性能报告
只写这些：
- 场景
- 指标
- 问题
- 优化前后对比

## 本周最终自检命令
```bash
go test ./...
go run ./cmd/server
```
