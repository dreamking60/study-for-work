# Week 01 Day 1：先把当前 CLI 看懂，再开始改

## 今天你要完成什么
今天不要急着加新功能。你先要搞清楚现在这份代码到底已经能做什么，不能做什么。

你今天的目标只有 3 个：
1. 跑通当前代码
2. 看懂当前目录结构
3. 把“现状结论”写下来

## 为什么第一天不能直接写代码
如果你连当前代码的真实状态都没确认，就开始改，很容易出现两种问题：
- 你以为没做，其实已经做了，结果重复劳动
- 你以为做完了，其实只是文档里写了，代码没有

这就是为什么第一天一定要先做“盘点”，不是浪费时间。

## 你今天工作的目录
```bash
cd ../../../go-backend-learning/week01-cli
```

## 第一步：确认代码现在能不能跑
先按顺序执行：
```bash
go test ./...
go run ./cmd/app run
go run ./cmd/app task-summary
```

你要记录的不是“通过了”这四个字，而是：
- 测试是不是全部通过
- `run` 输出了什么
- `task-summary` 输出了什么
- 有没有明显看不懂或不稳定的输出

## 第二步：按顺序读文件
今天只读下面这些文件，不要一上来扫全仓库。

### 入口层
- `cmd/app/main.go`
- `cmd/app/app.go`
- `cmd/app/args.go`

你要看明白：
- 程序从哪里开始
- 子命令怎么分发
- 参数是怎么解析的

### 配置层
- `internal/config/config.go`
- `internal/config/loader.go`
- `internal/config/parser.go`
- `internal/config/validator.go`

你要看明白：
- 默认配置从哪里来
- 配置文件怎么解析
- 非法配置怎么报错

### 模型层
- `internal/model/task.go`

你要看明白：
- 当前程序里的 `Task` 到底是什么
- 它现在只是练习模型，还是已经被命令真正使用了

## 第三步：写一份“现状结论”
今天必须写下来，不要只在脑子里想。

建议你直接写 5 条：
1. 现在已有哪些命令
2. 现在已经有哪些测试
3. 当前配置能力做到哪一步
4. 当前数据存储做到哪一步
5. 明天最该补的缺口是什么

## 你今天先不要做什么
- 不要实现 `task add`
- 不要改 module 名
- 不要重构整个目录
- 不要开始写 README

今天最重要的是搞清现状，不是追求产出数量。

## 今天完成后的标准
- 你已经跑过测试和命令
- 你已经读过入口层、配置层、模型层
- 你已经写下一份“现状结论”

## 如果今天卡住了怎么办
如果你在第一步就跑不通，不要继续读文档。先把错误抄下来，然后只回答两个问题：
- 是测试失败，还是命令失败
- 错误发生在入口层、配置层，还是其他地方

你明天的工作会依赖这个判断。

## 根据你之前报告补充的真实坑
- 如果你连 `go version` 都跑不出来，优先检查 `PATH`
- 如果 `import` 报 `missing import path`，先看自己是不是把 `import ()` 写成了别的符号

## 今天会用到的库和最小代码

### `testing`
今天你主要不是写测试，而是要能读懂测试最基本的样子：
```go
func TestSmoke(t *testing.T) {
    if 1 != 1 {
        t.Fatalf("unexpected result")
    }
}
```

### `os.Args`
你今天读入口文件时，大概率会看到参数来自哪里：
```go
func main() {
    fmt.Println(os.Args)
}
```

### `go test ./...` 为什么重要
- `./...` 表示当前模块下所有 package
- 这是你之后每天都会反复跑的最小验证命令
