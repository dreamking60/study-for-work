# Week 01 Day 2：给这份 CLI 一个明确定位

## 今天你要完成什么
今天不是写功能日，今天是“定角色”的一天。

你要把这份代码从“之前做过的 Go 练习”重新定义成：
- 后续项目的工程工具
- 调试工具
- 本地数据工具

如果不先做这件事，后面很容易继续把它写成一个越来越乱的小项目。

## 你今天要回答的核心问题
这份 CLI 未来服务谁？

答案不是“服务自己”，而是：
- 服务 `edge-gateway`
- 服务 `room-orchestrator`
- 以后可能服务 `cluster-operator` 的本地辅助工作

## 今天要改什么
今天主要改文档，不急着改代码。

建议你改的地方：
- `learning-plan/tutorials/week-01/README.md`
- 如果仓库里还没有 CLI 自己的说明文档，可以补一个最小 README

## 今天文档里必须写清楚 4 件事

### 1. 它现在是什么
建议写法：
- 这是一个工程 CLI，不是最终业务服务
- 它的职责是帮助后续项目完成配置调试、本地播种和运维辅助

### 2. 它现在已经能做什么
例如：
- 运行 `run`
- 输出 `task-summary`
- 支持基础参数解析
- 支持基础配置结构

### 3. 它现在还不能做什么
例如：
- 还没有完整配置文件支持
- 还没有真正的数据路径规范
- 还没有本地播种或回放命令

### 4. 它未来要增加什么类型的命令
今天先列名字，不实现：
- `seed`
- `replay`
- `export`
- `inspect`

## 为什么今天要把“还不能做什么”写出来
因为这是教程，不是宣传页。

如果你不把边界写清楚，后面学习时你会不断误判：
- 以为已经做完了
- 以为后续应该继续堆功能

教程最重要的不是“什么都能做”，而是“现在做到哪一步、下一步补什么”。

## 今天的产出最低要求
你至少写出下面这种结构：
```text
当前定位
当前能力
当前限制
后续命令方向
```

## 今天先不要做什么
- 不要开始写 `--config`
- 不要开始写 `--data`
- 不要做 task 子命令扩张

今天只做“定角色”。

## 今天完成后的标准
- 你已经能用一句话说清这份 CLI 的角色
- 文档里已经写出它服务哪些后续项目
- 文档里已经写出它现在的边界

## 今天会用到的库和最小代码

### `fmt`
今天虽然主要改文档，但你后面给 CLI 定位时，经常会在运行输出里写一句明确说明：
```go
fmt.Printf("tool=%s mode=%s\n", "opsctl", "local")
```

### 为什么今天几乎不用新库
因为今天的重点是“角色定义”，不是实现逻辑。

你今天最重要的不是 API，而是把下面这两句分清楚：
- 这是后续项目的工具层
- 这不是最终业务服务
