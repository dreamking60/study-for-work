# 项目总览（最终立项版）

## 立项原则
- 项目必须同时覆盖游戏服务器岗和云平台岗的核心能力。
- 项目之间要有上下游关系，避免三个互不相关的 demo。
- 已完成的 `week01-cli` 工作必须保留，并成为后续项目的工程基础。

## 项目 0：`opsctl`

### 定位
把当前 `go-backend-learning/week01-cli` 升级为统一工程 CLI。

### 为什么保留
- 你已经完成了配置、模型、参数解析、命令分发、测试这些基础工作。
- 这些能力对所有后续项目都有复用价值。

### 后续承担的职责
- 配置加载与环境切换。
- 数据播种、导入导出、回放。
- 本地调试命令、压测辅助命令、运维辅助命令。

## 项目 1：`edge-gateway`

### 目标
实现一个面向实时业务的接入网关，覆盖连接管理、鉴权、消息路由、限流、日志和压测。

### 对应岗位能力
- 游戏服务器岗：高并发、长连接、网络编程、在线体验保障。
- 云平台岗：统一接入层、稳定性、可观测性、服务工程化。

### 参考来源
- 主参考：`lonng/nano`
- 补充：`grpc-game-example`、Go 并发资料

### 最终可交付
- 可运行的服务。
- 最小协议文档。
- 连接 / 消息 / 限流主链路测试。
- 一份压测报告。

## 项目 2：`room-orchestrator`

### 目标
实现一个房间与任务编排服务，覆盖状态机、幂等、重试、补偿、超时回收、事件记录。

### 对应岗位能力
- 游戏服务器岗：房间生命周期、玩法流程拆解、可靠性。
- 云平台岗：任务编排、调度、故障恢复、工程设计能力。

### 参考来源
- 主参考：`Build an Orchestrator in Go`
- 补充：`Nakama` 的运行时和房间思路

### 最终可交付
- 状态机定义文档。
- 最小编排服务和任务流转测试。
- 异常场景演练记录。

## 项目 3：`cluster-operator`

### 目标
实现一个本地 K8s 环境中的部署控制面，用来管理 `room-orchestrator` 或相关房间服务实例。

### 对应岗位能力
- 游戏服务器岗：工具开发、运营支撑、服务部署理解。
- 云平台岗：Kubernetes、控制器、资源管理、CI/CD。

### 参考来源
- 主参考：Kubebuilder
- 补充：Go + Kubernetes DevOps 示例

### 最终可交付
- 一个最小 CRD / Controller。
- 在 `kind` 或同类本地集群中的部署验证。
- Docker / CI / 部署文档。

## 项目之间的关系
- `opsctl` 为另外两个服务提供本地数据和运维辅助。
- `edge-gateway` 把请求 / 消息接进系统。
- `room-orchestrator` 负责房间与任务生命周期。
- `cluster-operator` 负责把这些服务部署到更接近真实环境的控制面中。

## 为什么不再把数据层单独立项
- 数据库、缓存、事件记录仍然会做，但会内嵌到 `edge-gateway` 和 `room-orchestrator` 中。
- 这样更接近真实业务，也更容易讲清楚“为什么需要某种存储设计”。
